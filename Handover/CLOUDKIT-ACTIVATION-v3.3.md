# Bull v3.3 CloudKit Activation

This guide must be completed by the Apple Developer account owner. Source code alone
cannot create the App ID capabilities, signed entitlements or Production schema.

## 1. Developer portal and Xcode

Confirm these identifiers belong to team `8LT6DKBQL7`:

- App ID: `com.ahmed.Bull`
- iCloud container: `iCloud.com.ahmed.Bull`

On the Bull target, confirm these capabilities:

- iCloud > CloudKit with `iCloud.com.ahmed.Bull` selected;
- Push Notifications;
- Background Modes > Remote notifications;
- HealthKit;
- Time Sensitive Notifications.

Let Xcode refresh the provisioning profile. Build to a physical iPhone and inspect the
signed entitlements using `VALIDATION-v3.3.md`.

Apple references:

- [CloudKit container](https://developer.apple.com/documentation/cloudkit/ckcontainer)
- [CloudKit encrypted values](https://developer.apple.com/documentation/cloudkit/ckrecord/encryptedvalues)
- [CloudKit environment entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.icloud-container-environment)
- [Push environment entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/aps-environment)

## 2. Generate the Development schema

Use two physical devices and two different iCloud accounts. Install a development-signed
Bull build on both. A simulator-only test is insufficient for location and background
behavior.

1. On the owner device, create one enabled test Risk Zone.
2. Open Settings > Therapist Oversight > Set Up Oversight.
3. Invite only the therapist test account.
4. Accept on the therapist device and allow notifications.
5. Log one Urge State observation and create one protected-change request.
6. Approve or reject it on the therapist device and sync both devices.

In CloudKit Console, Development should now contain the system share type and Bull's
records in the custom zone:

- `cloudkit.share`;
- `BullTherapistSnapshot`;
- `BullTherapistDecisions`;
- encrypted `payload` fields plus non-sensitive schema/update metadata.

Do not create fake Production records by hand. Exercise the real create/accept/decision
flow so CloudKit generates the share schema correctly.

## 3. Verify scope before deployment

Inspect a Development snapshot through the Console where permitted. The encrypted body is
not intended for Console reading, so also use the therapist UI and the supplied projection
tests. Require that the therapist can see only the approved scope and never:

- Bull Routine, Bull State or Vigour;
- sexual-health or exercise data;
- HealthKit samples;
- exact latitude/longitude;
- free-form notes, triggers or next actions;
- general compounded-risk alerts.

## 4. Deploy schema to Production

After the Development two-device checklist passes, use CloudKit Console's **Deploy Schema
Changes** for `iCloud.com.ahmed.Bull`. Confirm the Production environment contains the
share, snapshot and decision types.

Apple's CloudKit guidance notes that `cloudkit.share` is generated by a real share cycle
in Development and must be deployed before Production sharing is relied on:
[Apple Developer Forums, CloudKit share schema guidance](https://developer.apple.com/forums/thread/841618).

Schema deployment is effectively one-way for released clients. Take screenshots/exported
schema records before deployment and do not reset the Development environment unless you
intend to discard its undeployed schema and data.

## 5. TestFlight Production gate

Upload a signed archive, install through TestFlight on the same two test accounts, and run
the full two-device checklist again. Confirm in Production logs that snapshot saves,
decision saves, subscriptions and share acceptance succeed.

CloudKit publication means the record save succeeded. It does not prove a silent push ran,
that a local therapist notification appeared, or that a human saw it.

## Operational limits

- One therapist participant is supported per owner share.
- One client share is supported per therapist app installation.
- Use a fresh/dedicated therapist installation; Bull is not a multi-client clinic portal.
- Silent push is best effort. Force quit, offline devices, iCloud outages, OS throttling and
  disabled notifications can delay visibility.
- Bull detects permission/monitoring degradation on its next execution opportunity. It
  cannot prevent uninstall, iCloud sign-out or iOS Settings changes.
- No custom server, delivery receipt or emergency escalation service exists.

## Production stop conditions

Stop rollout if the signed environment is wrong, any schema type is absent, a participant
can see excluded data, multiple participants are present, a decision can mutate anything
other than the exact local pending proposal, or revocation cannot be observed from the
therapist device after its next successful sync.
